# 技術ノート: 既知の制約と残課題

このパイプラインで何が確かめられていて、何が確かめられていないかをまとめる。
測定条件・既知の落とし穴・未解決の問いを、後から judgement を要する順に並べた。

## 現在の成果物

DeepSeek-V4-Flash-0731 を 50%(256 → 128 experts/層)まで刈り、MTPブロックを
削除したチェックポイント。166.9GB → 82.4GB。量子化は元のまま(ルーテッド
expertはFP4、非expert部はFP8)で、再量子化も再学習もしていない。

評価値は [README](../README.md) にある。校正データは日本語・英語・コード寄り
(`calib/mix-dsv4.json`)。

## 既知の制約

**圧縮前との直接比較ができない。** 原本166.9GBが評価ホスト(統合メモリ121GiB)
に載らないため、評価値は「絶対水準として妥当か」を見るヘルスチェックであって、
圧縮による劣化量の測定ではない。REAPの論文が50%で「ほぼ無劣化」としている点を
裏取りできていない。

**先頭3層はプルーニングではなくマージになっている。** この3層はトークンIDの
固定表(`tid2eid`)でexpertを選ぶ。`n_routed_experts` はモデル全体で1つの値なので、
他の層を刈るならこの3層も同じ数まで刈らざるを得ず、削除されたexpertを指していた
トークンIDは生存expertへ振り直される(`--hash-layers prune-remap`)。
ルーター行の向きが最も近い相手へ、負荷が偏らないよう均等割当で寄せているが、
**純粋なプルーニングではない**。この再割当の影響は個別に測っていない。

**MTPブロックを削除している。** 投機デコードは使えない。

**校正データを変えれば結果は変わる。** REAPは「自分のデータが実際に使うexpert」
を残す手法なので、別の言語・ドメインを狙うならスコアリングパスからやり直す必要が
ある。このチェックポイントの数値は、この配合に対する数値でしかない。

## 未解決の問い

### 因果マスクを直すと perplexity は改善し、選択式タスクは劣化する

スコアリングパスのドライバに、attention マスクが反転するバグがあった
(compressor の追加KVスロット分をマスクに継ぎ足す際、additive float の
`block_bias` を bool にキャストして 0 と -inf の意味が入れ替わり、未来が漏れる)。
`--attn eager` を既定にし、マスクが None または bool なら例外を投げるようにして
修正済み。

修正前後で saliency を比べると、50%時の保持expert集合は **Jaccard 平均 0.8223**
しか一致しない(128個中13〜14個が別物、層が深いほど乖離が大きい)。
両方でチェックポイントを作って評価した結果:

| 評価 | 修正前(sdpa) | 修正後(eager) |
|---|---|---|
| perplexity(262,016トークン) | 6.9126 | **6.5891** |
| JCommonsenseQA(1,119件) | **0.9258** | 0.9088 |
| MMLU(570件) | **0.6947** | 0.6526 |
| global_mmlu 15言語 | — | 13言語で低下(平均 −0.051) |
| RULER 4K/16K/32K/64K | 97.60/96.76/98.26/96.60 | 98.68/96.10/96.93/**94.51** |

**REAPが最適化している目的(校正分布上での出力の保存)は修正後のほうが正しく
測れており、perplexityがそれを裏付ける。しかしそれが下流の識別タスクの精度には
結び付かない。** 15言語中13言語で低下しているので偶然ではない(符号検定 p≈0.007)。

出荷しているのは修正後(eager)版である。**バグのある測定に基づく選択を、
ベンチマークが良いという理由で採用はしない**という判断による。ただし
「なぜ正しい測定のほうが下流で負けるのか」は説明できていない。

### 長文脈で落ちるのは検索ではなく読解

RULER の内訳を見ると、針の検索(niah系8タスク)は32Kまで全長さで1.000を維持する
一方、`ruler_qa_squad`(検索した箇所の読解)だけが 4Kの0.842から64Kの0.542まで
単調に下がり、4長さすべてで最下位になる。選択式タスクで負ける傾向と方向が同じで、
**プルーニングが失わせているのは検索能力ではなく、取り出した情報を使う能力**
である可能性がある。切り分けていない。

## 運用上の注意

**ECCなしのRAMでは、大きな読み書きの最中に静かにビットが化ける。**
出力82.4GBをSHA256で検証したところ、全体を通すたびに**違うファイル**が不一致に
なった(1回目は48個中1個、2回目は別の2個、1回目に失敗したものは合格)。
単独で読み直せば必ず正しい。約30GBに1回の割合で、MCE・EDAC・NVMeエラーの
いずれもログに出ない完全なサイレントエラーである。同日にメモリ逼迫で2回
ハードフリーズしたマシンでの観測。

**手元のコピーと公開物を突き合わせても、この種の誤りは検出できない**
(どちらも同じバイト列に由来するため)。検証するなら**元モデルと突き合わせる**。
REAPは生存expertの重みに触れないので、プルーニング後のシャード内でそれらの
バイト列は元のチェックポイントと完全一致していなければならない。これは
このパイプラインの設計そのものが提供している検証手段である。


**`--gpu-memory-utilization` は統合メモリ機では意味が違う。** その割合が
システムRAMから取られるので、vLLM既定の0.9は121GiB機で約109GiBを予約し、OSに
8GiBしか残さない。32Kでデコードが 0.1〜2.2 tok/s まで落ちた時、エンジンの
KVキャッシュ使用率は4〜6%しかなく、**KVプールは律速ではなかった**。この状態で
2つ目のクライアントを向けるとホストごとハングする(電源の入れ直しが必要)。
0.75 にすると約28GiBが残り安定する。

**lm_eval の `timeout` は待ち行列を含む1リクエストの総時間**で、既定300秒。
32Kではエンジンが6〜7並列しか流せず10件が待機して超過し、サーバーがまだ処理中
なのにクライアントがrunを殺す。長文脈は `num_concurrent=8` / `timeout=1800`。

**RULERの結果JSONには、成功した実行でも `4096,none: -1` が必ず入る**
(評価しなかった既定長のプレースホルダ)。これを見て失敗と誤読しないこと。
対象長のキーだけを見る。`run_ruler_sweep.sh` はそう検証している。

**perplexityのholdoutはモデルごとに作り直す。** 別モデルのトークナイザで作った
ファイルを渡すと、症状は数時間走った後の素の 400 Bad Request だけになる。

**64GBホストでスコアリングパスを回すと `--spill` が要り、律速はSSDの持続書き込み
になる。** hidden stateを毎層書き戻すため `--state` 込みで層あたり35〜40GBを書き、
コンシューマSSDはSLCキャッシュが枯れて層時間が77s→145sまで悪化する(全体80分)。
128GBあれば spill なしで約37分。

**スコアリングパスの前に必ず小規模スモークを打つ**(`--random-tokens 4,256
--max-layers 5`)。また**親プロセスでtorch演算をしてから `ProcessPoolExecutor`
を fork しないこと** — OpenMPスレッドプール初期化後のforkで子がデッドロックする
(`mp_context="spawn"` を使う)。

## 残課題

1. **より深いプルーニング率(62.5%、75%)を試す。** saliencyは計算済みなので
   サージェリパスを数分回すだけで作れる。50%では校正データの有無と言語別スコアの
   順位が対応せず、**用途特化が効いている形跡がない**。効き始める深さがあるのか、
   それとも効かないのかは分かっていない。
2. **校正データ512サンプルでの再スコアリング。** 現状256サンプル。
   128GBのRAMがあれば spill なしで回せる。品質が変わるかは未確認。
3. **ハッシュ層のマージの影響を単独で測る。** 3/43層とはいえ、純粋なプルー
   ニングではない唯一の箇所である。
4. **統合メモリ機でスコアリングパスを回した場合の実測。** 未計測。同程度か
   若干遅い程度と予想している。
5. **128K文脈の確認。** 現行のチェックポイントでは未測定。
6. **出力を元モデルと突き合わせる検証。** ECCなしのマシンで作った以上、
   サージェリパスの最中にビットが化けていない保証がない。生存expertのバイト列が
   元のチェックポイントと一致することを抜き取りで確認していない。
